## CC1：保存防重晚于异步编码，状态可能混用（P2）

位置：`src/components/GameDetailPage.vue:978`、`:993`、`:998`、`:1003`。

`saveCover` 在开始时读取图片并绘制 canvas，然后等待 `canvas.toBlob`；直到编码完成才设置 `coverSaving = true`。在此之前，保存、关闭、裁剪调整或新的截图读取都没有被该保存状态挡住。

复现一：保持第一个 `toBlob` 未完成，再调用一次真实 `saveCover`，两次都进入编码；放行两个回调后出现两次后端保存请求。后端游戏操作锁只能阻挡恰好重叠的请求，不能保证这两个请求只提交一次。

复现二：第一次绘制使用 A 图；等待编码时把当前原图与裁剪位置切为 B。最终请求包含 A 的展示图、B 的原图字节与扩展名、B 的偏移。编码后上传的字段不是同一份不可变快照。

建议：首个异步步骤前设置保存状态；一次性捕获原图、扩展名、几何与裁剪参数；整个生成和保存过程使用同一份快照，并以统一 `finally` 收尾。保存期间缩放与拖动也应遵守相同状态。

## CC2：关闭与卸载没有使异步图片读取失效（P2）

位置：`src/components/GameDetailPage.vue:819`、`:832`、`:896`、`:962`、`:1075`。

`openCoverFile` 以 `Date.now()` 作为加载标识，`readCoverBytes` 只在成功时比对标识。但关闭裁剪框与组件卸载只释放当前已挂上的图片，不更新加载标识，也没有统一的 disposed 检查。尚未触发的图片回调仍被视为有效；旧读取的失败分支还会无条件释放当前图片。

复现一：延迟 `arrayBuffer`，执行真实 `dismissCoverEditor` 后再放行，`coverEditorOpen` 和图片字节被重新写回。该单独复现中 `coverImage` 已被释放，因此不把“弹窗一定重新可见”作为结论。

复现二：开始图片解码后执行实际组件卸载回调，再触发图片加载完成。旧实例仍设置 `coverSourceUrl = blob:late`、图片及弹窗状态；该新挂上的 Object URL 没有再被回收。

建议：使用递增代次，并在关闭、切换源图和卸载时失效；所有成功与失败回调都检查代次和 disposed；尚未交给当前编辑器的 Object URL 由各自加载任务负责释放。

## CC3：在途截图准备请求可留下幽灵会话（P2）

位置：`src/components/GameDetailPage.vue:840`、`:845`、`:851`、`:1081`。

准备截图时，前端在 `armGameCoverCapture` 返回之前没有设置准备中的状态，也没有登记请求代次。用户此时离开详情页，卸载回调因尚无 captureId 而无法取消会话。随后 IPC 返回，已卸载实例仍保存 captureId 并最小化主窗口。

复现：延迟 arm 返回，执行真实卸载回调，再返回成功 captureId；仍发生一次窗口最小化，未调用 discard，实例中留下 pending 状态。真实后端的会话可继续占用全局截图状态，直至截图或 120 秒等待超时；期间新的 arm 会被已有会话阻挡。

建议：请求发出前进入准备状态；返回后先检查请求是否仍有效。若页面已离开，立即 discard 返回的会话，不执行最小化。重复点击和准备失败统一收尾。

## CC4：热键首次失败无法在进程内恢复（P2）

位置：`src-tauri/src/services/cover_capture_service.rs:75`、`:90`；`src-tauri/src/lib.rs:298`。

`HOTKEY_LISTENER_STATUS` 是 `OnceLock<Result<(), String>>`。首次注册冲突或两秒就绪超时都会成为该进程永久保留的 Err；后续调用初始化不会重新注册，而手动截图入口只读取缓存状态并直接返回错误。

复现：保留原样初始化函数，注册线程替身第一次返回冲突、后续本可成功。连续初始化两次仍都失败，实际只启动一次线程。这证明“关闭冲突程序后在当前 GameSaver 中再试”无法恢复，当前需要重启应用。

建议：成功监听实例保持单例，失败结果允许受控重试；监听就绪与线程是否存活分别管理，避免重试产生两个监听线程。超时后迟到的注册结果也应纳入同一状态管理。

## CC5：读取截图位图的 GDI 调用顺序违反约束（P2）

位置：`src-tauri/src/services/cover_capture_service.rs:440`、`:464`、`:476`。

截图先把 bitmap 选入 memory DC，再执行 BitBlt；调用 `GetDIBits` 时仍未恢复原先选中的对象，恢复发生在读取之后。Microsoft 的 [GetDIBits 官方文档](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-getdibits) 明确要求被读取位图在调用时不得选入任何 DC。

本次通过 HTTPS 取得该官方页面并核对约束，状态 200，摘录记录在 `.perf/cover-review-20261115/official-gdi-evidence.json`。这是源码与 API 契约核对，没有采集真实屏幕，也不能据此认定此前所有黑图或闪退都由这一点导致。

建议：BitBlt 后先恢复原对象，再读取 bitmap；检查对象选择和恢复结果，并让位图、DC、屏幕 DC 的释放覆盖每条错误路径。

## CC6：封面路径和旧图清理缺少完整的归属校验（P2）

位置：`src-tauri/src/commands/game_commands.rs:303`、`:442`、`:462`、`:512`、`:518`；`src-tauri/src/cover_protocol.rs:183`。

正常封面记录形如 `covers/<gameUid>/<coverId>/display.jpg`。当前 `safe_cover_path` 只拒绝绝对路径、上级分量和不同游戏的词法前缀，没有要求后缀确为一个封面版本中的文件。`cleanup_old_cover` 随后直接删除该路径的父目录。

隔离复现：

- 旧记录为 `covers/game-a/display.jpg`，换图清理删除整个 game-a 封面根，连刚保存的新封面一并删除。
- 旧记录为 `covers/game-a`，清理删除全库 covers 根，另一游戏封面也消失。
- 正常三层记录的对照测试通过，只删除旧版本，新图和其他游戏封面均保留。

生成记录和云端安装的现有正常写入点都使用三层路径，未找到它们主动生成前两种异常结构的证据。因此前两项应理解为损坏/异常记录下的破坏性边界缺口，不是当前用户正常换图必现。

物理路径另有缺口：在隔离夹具中，把 `library/covers/game-a` 建为指向另一夹具目录的 Windows junction，`safe_cover_path` 仍接受，实际读到库外图像，原样 `write_synced_file` 也可经该路径在库外写文件。测试不把 Rust 删除 junction 本身等同于必然递归删除 junction 目标。

此外，`validate_component` 允许 `first/second` 这样的多段相对路径；它不是“单个目录名”的严格校验。尚未找到正常生成的 UUID 会带此结构的证据。

建议：复用已有单段标识与 reparse/path 归属防护；读写封面校验物理归属；清理仅接受该游戏下明确的旧 coverId 目录，显式拒绝游戏封面根、全库封面根、当前新目录及意外目录结构。清理失败保留新封面并记录原因。

## CC7：云封面同步可乱序，失败时还会污染缓存（P2）

位置：`src-tauri/src/commands/game_commands.rs:343`、`:355`、`:376`；`src-tauri/src/services/cloud_manifest_service.rs:286`、`:384`、`:388`。

本地保存成功后，每次更换封面都启动独立线程上传到同一个远端 cover.jpg；本地游戏独占锁不覆盖这些后台上传，也没有同 gameKey 的上传次序或最新修订检查。

乱序复现：使用原样 `write_cover`，上传替身阻塞旧图 A，先完成新图 B，再放行 A。最终远端替身保存的是 A，云封面缓存也被 A 覆盖；本地刚保存的封面仍是 B。没有连接真实百度账号。问题在并发覆盖顺序，而不是断言百度自身如何调度网络请求。

失败复现：先写入成功的旧云封面缓存，注入新图上传失败。函数虽返回 Err，仍把新图写成缓存 cover.jpg。正常后台调用方使用 `let _` 忽略该失败，没有对应重试状态或错误日志。

源码进一步表明，旧 `cover.cache.json` 不会在这里失效；若远端元数据仍未变，后续 `load_cached_cover` 可以把未上传的新图当作旧远端的有效缓存。因此同机商店显示正确，并不能证明另一台设备能取到相同封面。

建议：同一游戏封面更新串行化，或合并为仅同步最新修订；上传成功后才更新远端缓存并同步/失效其元数据。失败保留本地封面、记录可诊断结果，避免把本地成功冒充为云端缓存成功。

## CC8：上传校验失败没有可见反馈（P2）

位置：`src/components/GameDetailPage.vue:809`、`:832`、`:906`、`:1350`、`:1366`。

文件过大、类型不支持和图片读取失败都写入 `coverError`。模板仅在裁剪弹窗内渲染此字段，而这些失败恰好发生在弹窗尚未打开时；主页面渲染的是另一个 error 字段。

复现：在未打开编辑器的状态传入 33 MiB PNG，真实函数设置了封面错误，但编辑器保持关闭、页面 error 为空；模板唯一的封面错误节点在关闭的弹窗内。用户体验就是选文件后没有反应。

建议：加载/校验阶段在详情页封面区域或统一提示中显示错误；裁剪和保存阶段在编辑器内显示，避免两个入口漏报。

## CC9：后端输入校验的防御性缺口（P3）

位置：`src-tauri/src/commands/game_commands.rs:399`、`:409`、`:419`；`src-tauri/Cargo.toml:53`。

`position.offset_x_milli.abs()` / y 的输入是 i32，最小值无法取同类型正数。原样函数隔离复现：debug 下 `i32::MIN` 触发 panic；关闭溢出检查的优化构建中，该值取绝对值后仍为负数，反而通过上限判断。正常裁剪 UI 不会主动生成该参数，本轮也没有声称该输入会使当前 release 安装包闪退。

图片检查只认开头魔数与元数据中的输出尺寸，不解码实际内容；四字节 PNG 标记配三个字节 JPEG 标记就能通过。正常浏览器图片解码和 canvas 编码会挡住多数坏图，因此这属于异常 IPC 输入的第二道防线不足。

建议：范围比较不要对不可信有符号整数直接取绝对值；图片校验使用受限的格式/尺寸解析，保留现有字节上限和明确的像素上限。不要为此引入庞大新流程。

## 修复结果（2026-11-15）

CC1—CC9 已修复。保留现有封面展示比例、上传格式、Ctrl + Alt + S 快捷键和前端调用接口，不增加前端配置开关。

### 前端保存与截图会话

- CC1：编码前即进入保存状态；原图字节引用、扩展名、裁剪位置和几何尺寸在同一时刻取得，编码与后端保存使用同一份快照。保存期间禁用缩放/拖动；编码失败也释放保存状态。离开页面时，尚未发出的保存 IPC 不再启动。
- CC2：图片加载改用递增代次，关闭/卸载立即取消；尚未交给编辑器的 Object URL 由加载任务回收。成功和失败分支都校验代次，旧读取失败不会清空新图片。`openCoverFile` 现在真实等待解码及字节读取完成，并返回是否载入成功。
- CC3：arm 请求发出前即锁定准备状态，重复点击不会再次发请求；离开后迟到的 captureId 立即 discard，不再最小化窗口。截图 fetch 同样检查会话代次；ready 事件比 arm 回复先到时，不会被迟到回复复活成无效等待会话。
- CC8：选图校验/读取错误在裁剪框尚未打开时进入详情页现有错误区域；编辑器内的错误继续就地显示。图片读取中有按钮禁用与提示。

### 后端监听与文件边界

- CC4：热键监听线程保持单例，注册冲突每秒受控重试；解除冲突后不必重启应用。初始化等待超时不会再新建一个线程，迟到成功仍可采用；监听线程异常退出后可通过手动截图入口重建。注册成功后不再重复注册，线程退出释放热键。
- CC5：BitBlt 后先恢复原选中对象，再调用 GetDIBits。检查选择/恢复失败，并在读取失败、选择失败和恢复失败时释放 bitmap、memory DC 和 screen DC；像素缓冲区校验/分配移到获取 GDI 资源之前。
- CC6：封面路径要求完整的 `covers/<gameUid>/<coverId>/<允许文件名>` 结构；标识严格限制为单段，拒绝 staging 路径与重解析目录。清理不接受游戏封面根或共享 covers 根，也不会清理与当前新图相同的目录。普通保存及云端安装封面共用封面服务的校验与写文件能力，写入成功才登记封面路径。
- CC9：裁剪偏移改为直接范围比较，不再对不可信 i32 取绝对值。后端实际解析并解码 PNG/JPEG/WebP，校验展示图确为 1280×720，限制图片像素和解码内存，拒绝只有魔数的坏图。
