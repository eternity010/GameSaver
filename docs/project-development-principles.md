# 项目开发原则与实践总结

> 本文提炼 GameSaver 重构过程中形成的通用项目开发经验。它不是某一个产品的需求文档，而是一套用于复杂桌面应用、工具软件和长期演进项目的设计与实施原则。

## 1. 核心判断

### 1.0 必要性优先

所有设计、字段、页面、状态和自动化行为，都先判断它是否必要：

- 当前用户是否真的需要；
- 是否解决已经确认的问题；
- 是否能显著提高可靠性、性能或体验；
- 是否值得承担额外的开发、测试和维护成本。

不必要的功能即使“以后可能有用”，也不应提前加入核心流程。优先采用最简单、可理解、可验证的方案；只有在真实需求出现并且简单方案无法解决时，才增加抽象和复杂度。

```text
先证明需要，再设计实现；先用简单方案，再考虑扩展。
```

### 1.1 先确定真正的管理单位

系统的核心管理单位必须来自用户的真实心智模型，而不是来自最早实现的数据库表或页面结构。

GameSaver 最初容易把“存档”当成主对象，但用户真正管理的是“游戏”：

- 添加的是游戏；
- 启动的是游戏；
- 本体、存档、版本和云端状态都属于某个游戏；
- 游戏库和游戏商店也都围绕游戏组织。

因此应该先确定聚合根，再决定数据结构、页面层级和服务边界。

通用原则：

```text
用户管理什么，系统就以什么为核心对象。
```

### 1.2 区分领域身份、显示名称和实现细节

一个名称不应该同时承担所有职责：

- 显示名称用于界面展示；
- 本机内部 ID 用于数据库关联；
- 跨设备或云端身份使用用户确认的稳定标识；
- 文件路径、ZIP 名称和远端文件 ID 只属于存储或传输层。

不要让随机 ID、文件夹名或接口字段反过来决定产品模型。实现细节可以变化，领域身份不应被轻易改变。

同时也要控制模型数量。身份模型只解决真实存在的问题，不为了“可能的未来场景”提前引入复杂指纹、评分系统和多级映射。

### 1.3 独立性与关联性同时成立

本地和云端应当是两个独立的数据域，但通过有限、稳定的关系进行关联：

- 本地没有云端也能运行；
- 云端不可用不应破坏本地功能；
- 删除本地不自动删除云端；
- 删除云端不自动删除本地；
- 上传、下载、覆盖和同步才是明确的跨域操作。

这是一种“弱耦合关联”，不是把本地和云端做成一个不可分割的对象。

### 1.4 复杂度必须有预算

正确不等于复杂。每增加一个属性、状态、策略或自动判断，都应回答：

1. 它解决了哪个已确认的问题？
2. 用户能否理解它？
3. 它是否增加了迁移、测试和异常处理成本？
4. 去掉它会造成什么实际损失？

如果一个简单的用户确认就能解决问题，就不应使用多属性推断、自动合并或复杂评分替代它。

## 2. 这套方法对应的成熟理论

你的思路不是一个单独的新理论，而是多个成熟实践的组合。它们共同形成了适合这个项目的工程方法。

| 实践判断 | 对应理论或方法 | 在项目中的体现 |
| --- | --- | --- |
| 以游戏而不是存档为主对象 | 领域驱动设计（DDD）、聚合根 | 游戏承载本体、启动、存档和云端状态 |
| 游戏库、商店、详情页分层 | 信息架构、限界上下文、关注点分离 | 本地库与云端商店职责不同 |
| 本地优先、云端增强 | Local-first、离线优先设计 | 百度网盘失败不阻断本地启动 |
| 本地与云端独立但可关联 | 松耦合、端口与适配器 | 云端 Provider 不直接侵入游戏核心模型 |
| 先做垂直闭环再扩展 | 增量开发、Walking Skeleton | 添加、启动、存档、本体包逐批完成 |
| 旧数据一次性转换 | 数据迁移、演进式架构 | 新模式只保留新模型，旧数据由迁移器转换 |
| 临时目录、原子替换、失败恢复 | 事务性工作流、Saga、补偿事务 | 本体更新、恢复和迁移失败时回滚 |
| 状态有限、内部细粒度 | 有限状态机、状态投影 | 内部任务状态多，用户界面只展示少量主状态 |
| ETW 优先、快照回退 | 渐进增强、分层降级 | 高精度能力不可用时保持可用性 |
| 传输任务独立显示 | 后台任务模型、事件驱动 UI | 传输中心统一展示进度和失败状态 |
| 内容寻址和哈希校验 | 内容寻址存储、不可变版本 | 存档 CAS、ZIP 完整性校验 |
| 危险操作多次确认 | 安全关键 UX、可恢复性设计 | 删除远端游戏前展示影响范围并二次确认 |

所以，准确的表述不是“你提出了一个已经存在的单一理论”，而是：

> 你在实际产品设计中，自然组合了 DDD、分层架构、增量交付、Local-first、事务性工作流和以用户为中心的 UX 原则。

## 3. 可复用的架构方法

### 3.1 先写领域模型，再写页面

推荐顺序：

```text
真实用户对象
    -> 生命周期
    -> 资源归属
    -> 状态和约束
    -> 服务边界
    -> 页面与操作
    -> 传输和存储实现
```

不要从“现有页面叫什么”或“当前表里有什么字段”开始设计新架构。页面只是领域模型的一个投影。

### 3.2 用资源边界组织模块

一个资源的创建、读取、更新、删除和恢复逻辑，应尽量保持在同一领域模块内；跨领域的部分通过明确接口调用。

GameSaver 的合理边界是：

- 游戏库：本地安装状态和游戏列表；
- 游戏详情：某一个游戏的启动、本体、存档和关联状态；
- 游戏商店：云端游戏和云端版本；
- 传输中心：跨游戏的后台传输任务；
- 平台设置：全局路径、账号和默认策略；
- 云端适配器：百度网盘 API 和远端清单。

入口层只负责注册和装配，具体业务实现下沉到领域服务或仓储模块。

### 3.3 业务独立，状态统一

不同模块可以独立工作，但必须共享同一套关键状态来源。否则会出现：

- 游戏库认为已安装，商店认为未安装；
- 详情页认为任务完成，传输中心仍显示进行中；
- 本地记录已更新，但云端清单还显示旧版本。

解决方式是：

- 后端保存权威状态；
- 前端通过任务和刷新读取真实结果；
- 缓存只用于展示性能，不能作为最终判断依据；
- 删除、安装和同步完成后重新读取状态。

### 3.4 复杂状态在内部，简单状态给用户

内部可以有 `pending`、`running`、`verifying`、`extracting`、`committing`、`rollback` 等阶段，但界面主状态应控制数量。

状态设计分为两层：

- 内部状态：服务、任务和日志使用，用于诊断和恢复；
- 用户状态：游戏卡片和详情首屏使用，用于帮助用户决定下一步。

用户不需要知道所有内部阶段，但必须知道当前是否可启动、是否需要处理、是否正在操作，以及失败后怎么办。

## 4. 可靠性与可恢复性

### 4.1 任何高风险操作都采用事务式流程

文件、数据库和远端操作通常无法真正共享一个数据库事务，因此使用“暂存 + 提交 + 补偿”的方式：

```text
预检
    -> 写入临时位置
    -> 校验结果
    -> 原子提交
    -> 更新记录
    -> 清理旧数据
```

如果中途失败：

- 原数据仍可用；
- 临时数据可识别；
- 启动时能够恢复或清理；
- 日志能够说明失败阶段。

### 4.2 先改变可回滚的状态，再删除不可逆数据

删除本体、删除云端版本和清理历史版本都应该遵循：

1. 验证目标范围；
2. 确认没有运行中的游戏或冲突任务；
3. 展示影响范围和预计释放空间；
4. 暂存或登记待删除状态；
5. 执行删除；
6. 重新读取并确认结果。

对不可逆的远端删除，确认强度应高于本地可恢复操作。

### 4.3 迁移不是永久兼容

长期保留旧模型会造成双轨逻辑、测试膨胀和概念混乱。更清晰的做法是：

- 旧数据进入迁移边界；
- 迁移器把旧结构转换成新结构；
- 校验并备份迁移结果；
- 新业务只使用新模型；
- 迁移成功后清理旧结构。

这叫“一次性迁移”，不是“运行时兼容”。两者的维护成本完全不同。

## 5. 性能方法

### 5.1 先测量，再优化

把一次长流程拆成可观测阶段：

```text
启动 -> 扫描 -> 捕获 -> 解析 -> 分析 -> 校验 -> 提交
```

每个阶段记录耗时、输入规模、输出数量和失败原因。没有这些数据时，优化只能依赖猜测。

### 5.2 优先消除无效工作

通常优先级是：

1. 不做不必要的工作；
2. 缩小扫描范围；
3. 缓存稳定结果；
4. 将非关键工作移到后台；
5. 最后才优化单个循环或算法。

例如：商店不应在应用启动时读取云端列表，而应在进入商店时懒加载第一页。这个收益通常高于微调卡片渲染。

### 5.3 让功能降级，而不是整体失效

高性能路径和可靠回退路径应同时存在：

- ETW 优先，快照作为回退；
- 原生 ETL 解析优先，CSV 作为回退；
- 云端不可用时保留本地能力；
- 缓存缺失时重新读取，而不是显示错误的旧数据。

降级必须被记录和展示，但不能把可选能力的失败扩大成核心流程失败。

## 6. 前端体验原则

### 6.1 页面应该对应用户任务

页面不是技术模块的目录，而是用户任务的工作区：

- 游戏库：找到并启动本地游戏；
- 游戏详情：管理当前游戏；
- 游戏商店：浏览和管理云端游戏；
- 传输中心：查看所有后台传输；
- 平台设置：修改全局配置。

如果用户需要跳转到一个技术名称页面才能完成自然任务，说明信息架构仍然偏向实现，而不是偏向用户。

### 6.2 破坏性操作必须清楚、可预期

确认不是为了增加点击次数，而是为了让用户理解后果。确认内容至少说明：

- 操作对象；
- 删除或覆盖范围；
- 不受影响的内容；
- 是否可恢复；
- 预计释放的本地或云端空间。

危险操作应与普通操作在位置、颜色和交互上区分开。

### 6.3 长任务必须有独立状态空间

压缩、上传、下载、解压和校验不能只依赖弹窗或短暂提示。应提供：

- 阶段名称；
- 百分比和当前处理对象；
- 取消入口；
- 失败原因；
- 基于原任务参数的重试；
- 重启后的异常中断状态。

## 7. 开发流程

### 7.1 先形成设计约束，再拆批次

每个批次都应有明确的：

- 目标行为；
- 不改变的行为；
- 数据边界；
- 错误和取消路径；
- 验证方式。

批次不应按“改几个文件”划分，而应按“完成一个可验证的用户闭环”划分。

### 7.2 每批次都经过四个检查点

```text
定位现状
    -> 小范围实现
    -> 自动验证
    -> 用户场景验证
```

自动验证包括编译、单元测试、类型检查和差异检查；用户场景验证包括安装、启动、取消、失败、重试、恢复和删除。

### 7.3 设计文档是约束，不是装饰

设计文档应持续回答：

- 当前系统的核心对象是什么？
- 哪些模块属于哪个边界？
- 哪些数据是本地的，哪些数据是云端的？
- 哪些操作会跨边界？
- 失败时如何恢复？
- 当前阶段完成到哪里，下一阶段是什么？

实现前先对照文档，发现代码与模型冲突时先修正方向，不要为了让旧结构继续工作而不断增加例外。

## 8. 最终提炼

可以把这套方法压缩成十句话：

1. 时刻判断什么是必要的，拒绝无收益的复杂化。
2. 先找准用户真正管理的对象。
3. 领域模型先于页面和数据库字段。
4. 显示名称、内部 ID 和存储路径不要混为一谈。
5. 独立模块通过少量稳定关系关联。
6. 新架构用一次性迁移进入，不用永久兼容拖累。
7. 高风险文件和远端操作必须可回滚、可恢复、可诊断。
8. 性能优化先减少无效工作，再做局部优化。
9. 内部状态可以详细，用户看到的状态必须简单。
10. 每个开发批次都要完成一个可验证的真实闭环。

这套原则最接近“以领域为核心的渐进式、可恢复、本地优先产品工程”。它不是一个全新的学派，但把成熟理论按照你的产品判断组合成了一套相当完整的实践框架。
