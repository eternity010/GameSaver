实现主要位于 `src-tauri/src/services/game_removal_service.rs`，包括边界校验、事务阶段、回滚、清理和启动恢复。现有命令层负责操作认领、任务与持久化回调，启动入口负责接线；仅新增这一份高内聚的业务模块，没有批量重建核心文件。`retry_game_removal` 已同时实现、注册并接入前端 API 与传输中心。

## GR1：完整删除缺少受管路径边界校验（P1）

位置：`src-tauri/src/commands/game_commands.rs:590`、`:610`、`:676`。对照：`src-tauri/src/commands/game_body_commands.rs:493`。

完整删除从 store 中取出 managed_path 后直接作为递归删除目标，只检查传入游戏 ID 非空。卸载本体则会验证 managed_path 是否等于当前 games_root/game_uid；两条破坏性操作没有使用相同的安全边界。GameRepository 读取时的 normalize 只要求该路径非空，不保证它位于受管库内。

触发前提是游戏记录中的路径错误、被改写或失去受管归属。本项不表示正常添加游戏必然删除源目录；现有正常记录通常是正确的。问题在于发生记录异常后，破坏性命令仍会删除库外路径，而不是拒绝操作。

复现：在隔离目录中建立 library/games 与另一个 external-source/game-a，将后者写入游戏记录。卸载校验拒绝该记录；完整删除的实际目标收集与删除函数却成功删除 external-source/game-a。全部路径均限制在测试 fixture 内。

建议：复用本领域的受管路径与单段 ID 校验，对所有删除目标做归属确认；根目录读取或验证失败必须终止删除，不应静默缩小清单。不要把路径校验替换成按文件数量或哈希扫描。

## GR2：卸载恢复直接清理未提交本体（P1）

位置：`src-tauri/src/commands/game_body_commands.rs:432`、`:441`；`src-tauri/src/services/game_body_update_service.rs:93`、`:440`。

卸载顺序为“将本体改名成 .<uid>.uninstalling-<随机值> → 检查取消 → 保存卸载状态 → 删除暂存本体”。这段逻辑没有记录暂存目录对应的提交阶段。

如果在改名之后、保存状态之前退出，磁盘游戏记录仍是 Active，原路径却不存在。启动恢复只按 .uninstalling- 名称识别目录，然后无条件递归删除，不检查记录是否已提交卸载，也不尝试恢复原路径。保存失败且改名回滚也失败时，同样只剩这份可回滚本体，下一次启动仍会直接清理。

复现：保存 Active 记录，执行实际改名步骤，在保存新状态前模拟中断，再调用原样启动清理函数。旧记录仍为 Active，但原目录与暂存目录均不再存在。这里没有模拟整个应用被操作系统终止；模拟的是精确提交窗口留下的磁盘现场。

建议：使用小型卸载提交记录。未提交时恢复改名，已提交后才续作清理；恢复失败时保留现场并报告。改名不会额外复制整份本体，不需要引入长期保留的完整游戏备份。

## GR3：完整删除中断留下没有记录的本体（P2）

位置：`src-tauri/src/commands/game_commands.rs:644`、`:720`、`:737`。

完整删除先将游戏、保护配置、存档版本和本体版本记录持久化摘除，然后启动后台线程删除目录。若在摘除后、文件删除完成前崩溃或退出，磁盘记录已丢失原删除清单；正常 UID 名称的游戏目录也不属于启动恢复识别的更新、卸载或放弃暂存目录。

复现：调用原样 detach_game_from_store，确认隔离 store.json 已无游戏，再调用启动暂存清理，原受管 game.exe 仍存在。现有任务记录仅保存游戏 ID 与进度，不能重建先前取出的完整路径清单；重启将任务标记为 interrupted 也不会执行清理。

建议：摘除前保存已校验的删除意图及目标，后台成功后清除；启动时续作未完成清理。不要删除全部“不在 store 的目录”来修复，否则会扩大误删范围。

## GR4：删除清单仍使用旧资源布局（P2）

位置：`src-tauri/src/commands/game_commands.rs:614`、`:620`、`:633`、`:644`；`src-tauri/src/app_state.rs:446`、`:450`；`src-tauri/src/repositories/save_repository.rs:312`、`:1841`。

当前封面位于 libraryRoot/covers/<uid>，本体包位于 libraryRoot/body-packages/<uid>，存档对象位于 libraryRoot/saves/.gamesaver-repository/objects/sha256。完整删除却尝试清理 games/covers/<uid>、appData/cache/body_packages/<uid> 以及旧的 games/.versions/<uid>。

同时，摘除 save_versions 后没有调用现有 CAS 标记清扫。删除最后一个游戏时，该游戏独占引用的对象可能继续占用空间，直到以后触发其他全局 GC。

复现：在当前布局创建封面、ZIP 和被该游戏存档版本引用的示例对象，调用原样摘除及文件清理。受管本体被删除，但三类资源均留下，删除函数仍返回无失败项。测试对象使用短示例哈希，只用于证明清理调用范围，不用于模拟对象恢复或哈希校验。

边界说明：现有 `lib.rs:155` 会在启动时清理未引用的 ZIP，因此不能将该 ZIP 残留描述成“永远无法回收”。当次删除没有及时释放它，重启且启动清理成功时通常可回收；封面没有发现对应孤立清理，CAS 仍依赖其他 GC 入口。

建议：从现有库根访问器取得当前布局；存档版本引用成功持久化移除后，再用现有仓库锁和全库引用清单回收无引用对象，保留其他游戏共享对象。不要按游戏 ID 直接删除共享 CAS 目录。

## GR5：清理未完成在界面上不可见（P2）

位置：`src-tauri/src/commands/game_commands.rs:707`、`:793`；`src/taskFeed.ts:62`；`src/components/TransferCenter.vue:26`；`src-tauri/src/commands/game_body_commands.rs:372`、`:461`。

完整删除虽然将失败目录写进任务消息与 failedPaths，但任务分类为 Maintenance，而实际前端分类策略的 visible=false，传输中心会过滤整条任务。详情页在命令返回后立即离开，没有其他相应的终态提示。因此注释中“任务卡片始终显示消息”的假设与实际挂载关系不符。

卸载清理失败时 worker 返回 Ok({cleanupPending:true, cleanupPath, removedBytes})，外层仍固定显示“游戏本体已卸载”。列表 DTO 不传 result，传输中心也不读取 cleanupPending，用户无法从该成功提示知道暂存本体仍占用空间。removedBytes 此时还是删除前统计的总大小，不是实际释放的字节数。

复现：实际 taskPolicyOf 确认完整删除任务被过滤；Windows 测试在改名及状态提交后，对暂存 game.exe 持有不共享删除的文件句柄。实际卸载 worker 返回 cleanupPending=true，文件仍在；释放句柄后，实际启动清理能够清掉它。没有声称卸载残留缺乏任何启动清理。

建议：让用户操作的删除任务有可见入口；将清理未完成与实际位置写入任务摘要，提供安全重试。卸载可以区分“已从本地移除”与“磁盘清理完成”，不要把未释放的大小报告成已回收大小。

## GR6：不可逆清理阶段仍接受取消（P2）

位置：`src-tauri/src/commands/game_body_commands.rs:435`、`:441`、`:461`；`src-tauri/src/services/task_service.rs:180`、`:211`；`src/taskFeed.ts:27`、`:90`。

卸载只在改名后检查一次取消，保存卸载状态后直接扫描和递归删除，不调用现有 begin_commit。任务的 cancellable 仍为空，BodyTransfer 默认允许取消，后端 cancel 也会返回成功。

复现：用原样卸载 worker 与 TaskService，在实际进度推进到 80% 时注入 cancel。cancel_requested 已变成 true，但 worker 仍完整删除本体并正常返回。实际前端策略在该阶段仍提供取消按钮，确认文案又承诺“未完成的部分不会生效”。

建议：可回滚阶段响应取消；不可逆提交前调用现有 begin_commit 原子拒绝迟到取消，并使界面显示不可取消。不要在已经删除部分文件后把任务标为取消成功。

## GR7：卸载终态没有及时刷新游戏库（P2）

位置：`src/components/GameDetailPage.vue:473`、`:671`、`:1074`；`src/App.vue:371`、`:68`。

uninstallBody 将 await watchTask 当成等待整个任务结束，但 watchTask 在第一次读取仍为 running 时只设置定时器便返回。调用方马上 emit refresh/back，组件卸载后清除后续轮询和事件监听。

此时若本体目录还没改名，刷新仍会读到游戏。App 根任务观察器只针对会话、安装、档案恢复与库迁移终态刷新，没有卸载终态。当前游戏库有 30 秒 TTL 定时兜底，所以这是没有及时刷新的旧卡片问题，不能描述成“必须重启才会消失”。

复现：执行实际 watchTask、uninstallBody 与 stopPolling，首次任务为 running/20% 时已触发 refresh/back；模拟卸载组件后定时器被清空。再执行实际 App 任务观察器，输入卸载 running→success，不会调用 scheduleLibraryRefresh。

建议：在全局任务终态中处理卸载和本地删除的库失效，避免依赖即将卸载的详情组件；或明确等待终态后再离开。保留已有 TTL 作为兜底即可。

## 未列为已确认缺陷的观察

AppState::claim_operation 不检查 running_games。把“删除前运行检查 → 启动服务登记 Launching → 删除认领操作”按这个顺序交错，状态层确实允许运行登记与删除独占同时存在；隔离测试证明了这一点。

不过当前 launch_game、uninstall_game_body、remove_game_from_library 都是默认同步 Tauri 命令，并且生产代码里只发现该命令调用 LaunchService::launch。现有证据未证明这几个入口能在真实 IPC 调度中按上述方式并发交错。因此本轮不将其计入已确认问题，也不声称已经复现“运行中的真实游戏被删除”。以后如将任一准入段移到异步工作线程，应把运行检查与独占认领放在一致的锁顺序下。
