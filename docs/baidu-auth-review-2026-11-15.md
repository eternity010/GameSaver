## BA1：云存档入口没有取得刷新凭据（P2）

位置：`src-tauri/src/commands/cloud_save_commands.rs:464`、`:469`；`src-tauri/src/services/cloud_save_service.rs:585`；`src-tauri/src/services/baidu_netdisk_service.rs:180`、`:197`。

本体上传和下载通过 `load_configured` 加载 AppKey、SecretKey，并建立 `RefreshContext`。云存档命令的共享加载函数和云存档概览却直接调用 `load_from_app_data`；即使平台已保存完整凭证，它们也会构造没有刷新上下文的客户端。

结果：云存档在 Access Token 完全过期时会在加载阶段失败；长任务在 Token 中途失效时也不能自行刷新。进入平台设置触发另一条具备刷新能力的入口后，问题可能暂时消失，容易误判为偶发网络故障。

隔离复现使用同一个临时数据目录，先保存假配置与未过期 Token：普通加载入口的 `refresh_context` 为 `None`，配置入口为 `Some`；对普通客户端强制刷新得到 `false`。没有访问真实刷新接口。

建议：云存档调用统一使用现有 `load_configured`，不要再复制应用凭证加载逻辑；补充“已配置凭证且 Token 到期”的调用级回归。

## BA2：Token 替换中断后不恢复，可能选错账号（P1）

位置：`src-tauri/src/services/baidu_netdisk_service.rs:1096`、`:1107`、`:1124`、`:1143`。

Token 写入仍自行执行“临时文件 → 主文件改名为备份 → 临时文件改名为主文件”，读取却只检查主文件。项目已有的 `store_file::load_with_recovery` 没有用于 Token。

如果应用在两次改名之间异常结束，目录中虽然存在可解析的备份或临时文件，重启后也会显示未授权。更严重的是：`token_paths` 随后会查找旧项目 `com.gamesaver.desktop` 的 Token；如果那里属于另一个百度账号，当前应用会静默改用那个账号。读取不持写锁，也存在提交窗口内误读的可能。

两种场景均已在临时目录复现：没有旧项目 Token 时，明明存在备份却读取失败；存在假旧账号 Token 时，实际返回旧账号及其路径。没有读取用户机器上的旧项目凭证。

建议：Token 采用统一存储与恢复逻辑，读写遵守同一同步边界；禁止自动跨项目借用凭证。历史导入如确有需要，应为明确的一次性用户操作。

## BA3：应用凭证与授权会话没有统一失效边界（P2）

位置：`src-tauri/src/commands/baidu_config_commands.rs:27`、`:42`、`:107`、`:149`；`src/components/PlatformSettings.vue:186`、`:234`、`:248`、`:322`、`:342`。

保存新 AppKey 或 SecretKey 只更新配置文件，已有 Token 没有绑定校验或失效处理。客户端会继续使用旧应用的 Access Token，却带着新应用密钥执行后续刷新。实际配置与客户端复现中，Access Token 仍属于 `app-a`，刷新上下文已经变为 `app-b`，状态查询仍报告已授权且没有刷新错误。

前端保存后也不清理已生成的旧授权 URL、旧 Code 或已连接状态。两个按钮分别只检查 `saving`、`authorizing`，可以在旧配置的换码请求尚未结束时保存新配置；后端换码在发请求前读一次配置，收到结果后没有再次校验配置是否已经改变，因此旧请求仍可提交 Token。

实际 Vue 函数隔离复现了三点：保存新凭证后旧 URL 仍在、状态仍显示“已连接”、换码等待期间仍可完成保存。后端交错提交的结论来自配置读取和 Token 提交之间缺少一致性检查的源码链路，不声称已向真实百度接口复现。

建议：配置发生实质变化时使相应授权失效；授权流程捕获本地凭证修订号，提交前再次核对。前端清理旧 URL、Code 和账户状态，保存与换码期间互相禁止重入。

## BA4：旧任务可能接受新账号 Token 继续重放（P1）

位置：`src-tauri/src/services/baidu_netdisk_service.rs:348`、`:357`、`:359`、`:361`。

刷新入口只判断磁盘 Access Token 是否与内存不同；只要非空且不同，就直接替换客户端 Token 并返回成功，没有区分“同一授权的刷新”和“用户重新授权了另一个账号”。原来为账号 A 创建的客户端，在鉴权失败后可能改用账号 B 重放原来的路径操作。

这对按远程路径删除、覆盖或多步骤提交的任务尤其危险；不能把同一个网盘路径误认为属于同一个账号。本条确认的是客户端可跨账号采用 Token 的能力，没有对真实网盘执行任何删除或覆盖。

实际客户端复现：以假账号 A 构造客户端，再把假账号 B 写到同目录，调用 `refresh_token(true)` 后客户端已使用 B。额外复现还确认：把磁盘替换为已过期但字符串不同的 Token，也会返回刷新成功，尽管客户端随即仍判断它已过期。

建议：采用本地授权修订号或等价的会话失效机制区分刷新与重新授权；旧任务遇到授权替换应明确停止，不得自动跳到新账号。采纳磁盘 Token 时同时验证其可用性。

## BA5：同一失效 Token 的并发请求重复刷新（P2）

位置：`src-tauri/src/services/baidu_netdisk_service.rs:348`、`:357`、`:364`；`:963`、`:973`。

`TOKEN_REFRESH_LOCK` 确保刷新串行，却不确保同一次失效只刷新一次。两条请求都携带旧 Token 失败后，第二个线程取得锁时才读取客户端当前 Token；此时第一个线程已更新内存和磁盘，两者再次相等，且 `force = true` 会跳过有效期判断，于是又发一次刷新请求。

隔离测试原样抽取 `access_token`、`token_is_stale`、`store_token`、`refresh_token` 四个方法，只有 HTTP 刷新替换为计数并落盘的假实现。用双线程屏障保证两条请求失败时观察到相同旧 Token，最终刷新次数为 2。没有把网络替身的结果表述为真实百度令牌轮换行为。

建议：把实际失败请求所使用的 Token 或修订号传给刷新入口，持锁后若当前授权已前进则沿用，不再次刷新；不要只在取得锁后读取一个新的“当前值”来比较。

## BA6：授权失败识别漏掉已支持的 `error_code` 响应（P2）

位置：`src-tauri/src/services/baidu_netdisk_service.rs:1080`、`:1092`、`:1290`。

普通 API 错误解析器支持数值型 `error_code`，但刷新判断只检查 HTTP 401、`errno` 和字符串 `error`。当响应以 HTTP 200 加 `error_code = 110/111` 表示 Token 无效或过期时，会直接返回业务错误，不执行自动刷新。

原样函数测试确认同一构造响应被 `parse_value` 判为错误，却被 `is_auth_failure` 判为非授权错误。这里验证的是处理特定响应结构的程序行为，没有声称所有真实百度接口都会返回该结构。

另一个同域边界是：JSON 请求在识别 HTTP 401 前先解析 JSON；非 JSON 的 401 响应会在刷新判断前退出。该点来自源码顺序核查，未单独做真实网络复现，也不另计一个问题。

建议：统一支持现有解析器接受的授权错误字段；HTTP 状态判断与可选 JSON 解析分层处理，并保持只刷新重放一次。

## BA7：刷新失败原因被请求包装器吞掉（P2）

位置：`src-tauri/src/services/baidu_netdisk_service.rs:973`、`:1001`；`src/components/PlatformSettings.vue:336`。

`request_json_value` 和 `send_raw` 通过 `matches!(self.refresh_token(true), Ok(true))` 决定是否重放，导致 `Err(...)` 被直接丢弃。缺少 Refresh Token、配置错误、刷新服务不可达、落盘失败等原因最终变成原请求的通用鉴权错误或 HTTP 401，无法告诉用户应重试还是重新授权。

隔离测试使用真实客户端请求包装器和一个只监听随机回环端口的 HTTP 假服务：服务返回 Token 已过期，客户端具备假应用密钥但缺少 Refresh Token。实际错误仅剩 `(111)`，缺失原本明确的“没有 refresh token，请重新授权”诊断。没有访问外网或真实凭证。

设置页另有同域文案问题：任何 `refreshError` 都追加“请重新完成百度授权”，把临时网络失败也导向重新授权。此处列为同一个诊断缺陷，不另计条目。

建议：保留原业务请求与刷新错误上下文，区分暂时网络失败、永久授权失效和本地持久化失败。错误继续遵守现有去 URL 和日志脱敏边界。

## BA8：Token 明文落盘（P2）

位置：`src-tauri/src/services/baidu_netdisk_service.rs:1124`、`:1129`；对照 `src-tauri/src/repositories/baidu_config_repository.rs:176`。

应用 SecretKey 已由 Windows DPAPI 加密，但 Access Token 与可用于续期的 Refresh Token 直接序列化为明文 JSON。提交中断时，临时文件和备份也可能携带明文。凭证生命周期的保护边界不一致，复制应用数据目录就会携带可用的云端访问凭据。

使用实际 `save_token` 保存假数据，随后读取临时目录文件并断言两种假 Token 字符串均可直接找到。没有查看或输出真实 Token。

建议：Token 同样采用本机加密的存储封装，结合 BA2 一并实现原子写入和恢复。明文旧文件如需要迁入，完成加密提交后再清理对应残留，不自动借用旧项目的账号。

### 验证口径
