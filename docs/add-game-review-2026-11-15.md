# 添加游戏完整流程审查

日期：2026-11-15。项目：`D:\code_program\GameSaverNext`，版本 1.0.31，基于当前工作区。此前云端安装、云存档、平台档案、迁移、删除及本体更新的修改保持原状。

范围：选择来源与启动程序、3 GB 提醒、预检与复制、登记待设置游戏、启动 ETW 学习、分析与手动范围、确认保护并激活、返回游戏库，以及取消、离开页面、普通失败和应用中断后的收尾。

初始审查阶段仅做审查与隔离复现。下文 AG1—AG10 和原始行号记录修复前的证据；本次修复与验证结果见文末。测试只操作自动清理的小型夹具，没有扫描、复制、删除真实游戏，没有启动真实游戏或 ETW，也没有操作真实存档、凭证或网盘。未构建安装包、提交或推送 Git。

## 结论

发现 10 项问题：2 项 P1、8 项 P2。优先修复“放弃添加”的恢复现场与破坏性操作边界，其次补上向导接续、重复操作准入和复制中断收尾。正常复制的已有测试通过，但没有覆盖这些流程边界。

## AG1：失败回滚的本体会被启动清理删除（P1）

位置：`src-tauri/src/commands/save_commands.rs:562`、`:583`、`:600`；`src-tauri/src/services/game_body_update_service.rs:672`。

`discard_pending_game` 先把正式目录改名为 `.<uid>.discarding`，再保存删除游戏记录后的配置。配置失败时尝试把目录改回去，但使用 `let _ = fs::rename(...)` 丢弃回滚失败，返回值只剩原配置错误，没有保存待恢复记录。

启动清理沿用“放弃目录已经与游戏库解耦”的假设，只按 `.discarding` 名称递归删除，不核对 store 中是否仍有这个游戏，也不知道上一次回滚曾失败。本体更新事务的修复会保护更新日志关联目录，但放弃添加没有对应日志，因此不受该保护。

复现：夹具含唯一一份受管 `game.exe`，先正常持久化待设置游戏。对放弃的配置提交注入失败，同时在原位置制造只读普通文件，使 Windows 明确拒绝目录改名回滚。放弃返回错误，原游戏记录仍在，完整受管本体保存在 `.discarding`；随后调用实际启动恢复/清理函数，`.discarding` 被删除，记录指向的位置没有可启动本体。

边界：这是组合故障注入，不代表正常放弃必然丢失文件；原始添加来源也不由该测试删除。风险在于恢复现场会被误认为垃圾，游戏学习期间写在受管目录内的新内容可能只能在该现场找到。

建议：将放弃添加纳入现有删除/事务机制；回滚失败上报并保留可恢复记录，清理前确认记录已成功摘除，恢复失败不删除现场。正常成功后仍释放本体空间，不增加长期副本。

## AG2：放弃添加缺少破坏性操作边界（P1）

位置：`src-tauri/src/commands/save_commands.rs:562`、`:580`、`:583`、`:590`。

该命令只在第一次读取记录时验证 `PendingSetup`，随即依据 `managed_path` 改名并后台递归删除。没有核对目标是否为当前库的 `games/<gameUid>`，也没有复用受管路径、junction 或现有全局迁移/游戏独占检查。

两项独立隔离复现：

- 将夹具记录的 `managed_path` 指向夹具内、受管 games 根以外的 `external/game-1`，实际命令成功摘除记录并删除该外部目录。触发前提是记录异常；不能说正常生成的路径都会越界。
- 设置实际 AppState 的 `LIBRARY_MIGRATION_KEY`，模拟迁移已取得独占状态，再调用实际放弃命令，操作仍成功并删除本体。说明前几轮在其他入口增加的迁移互斥没有覆盖这里。

建议：复用已有删除服务的目标归属和独占准入，在取得操作权后重新加载并核对待设置记录。无需为放弃入口再建立一套平行锁或重复的路径安全实现。

## AG3：向导离开或重启后无法继续设置（P2）

位置：`src/components/AddGameWizard.vue:26`、`:45`、`:581`；`src/App.vue:740`、`:782`；`src/components/GameDetailPage.vue:1159`；`src-tauri/src/commands/save_commands.rs:800`。

复制成功即持久化 `PendingSetup`，并不等用户最终确认保护范围。页面状态、任务 ID 和学习 session 只在向导组件内；侧边栏可以切走，`v-if` 会卸载组件，卸载只停止本地定时器。重新进入时从空白 form 开始，父组件没有传入待设置游戏或会话。

游戏库会展示待设置游戏，但详情页只显示“需要完成设置”，没有再次进入添加向导/学习的调用。其手动修改范围入口只能更新已经存在的保护配置，不能给待设置游戏创建配置。再次添加同一 key 又会被已有本体的待设置记录拒绝。

前端隔离验证确认新挂载组件没有 game/session/task 上下文；调用链审查确认没有接续入口。用户只能移除后重新复制，或使用开发接口处理。学习会话离开向导后也无法从界面接回；本项没有启动真实 ETW 证明资源长期占用。

建议：游戏库对待设置游戏提供“继续设置”，向导接收已有游戏上下文；保留成功复制的本体，并从后端查询可接续任务/学习会话。普通离开页面不应要求重新复制整份游戏。

## AG4：同一游戏可被重复添加（P2）

位置：`src-tauri/src/commands/add_game_commands.rs:54`、`:97`、`:179`；`src-tauri/src/services/game_library_service.rs:7`；`src/components/AddGameWizard.vue:195`、`:215`。

同 key 检查只发生在复制任务创建之前，当时没有为该 key 登记“添加中”。两个请求在第一份复制完成前都能通过；每次生成不同 UID，因此提交时 `register_pending` 的 UID/path 去重也不会拒绝。持久化 normalize 不按 key 合并，两份本体及重复 key 都能保留下来。

实际添加命令隔离复现：只在“开始检查目录”的任务事件处暂缓两个 worker，顺序发起两次相同 key 的添加，随后同时放行。两任务均为 Success，内存和落盘 store 均有两条相同 key、不同受管目录的记录，两个目录都含完整夹具本体。没有改写命令业务分支。

界面上的复现入口并非只能绕过按钮：`watchTask` 遇一次 `getTask` 读取失败就清空 `taskId`，回到 form，不取消实际后台复制，也不继续查询。用户以为失败再试，便可与仍在执行的第一次添加重叠。前端隔离测试已复现这段状态变化。

建议：对 gameKey 做原子添加准入，成功、失败、取消及中断恢复均正确释放/接管；入库前再检查一次唯一性。临时 IPC 失败保留任务 ID 和上下文，重试跟踪而不是把真实后台任务当作已经结束。

## AG5：学习启动存在重复会话窗口（P2）

位置：`src-tauri/src/commands/save_commands.rs:20`、`:38`、`:48`、`:96`；同文件的 `start_save_candidate_verification_task:144` 有相同形态。

命令只检查当前已经登记的 learning_sessions 与 running_games，然后创建后台任务。真正的会话及 runtime 在启动服务返回后才写入；启动期间没有登记占位或取得该游戏的独占操作。因此第二次请求可在第一次尚未返回时通过相同检查。

隔离测试执行原样 `start_save_learning_task`、真实 AppState 和 TaskService，只在学习服务适配器中暂缓返回。连续两个请求均成功，最终 learning_sessions 中存在同一游戏的两份会话。它证明了准入和会话登记缺口，不是实际启动两份游戏或 ETW 的端到端复现。实际服务在每次调用中会生成独立 session 并尝试启动 ETW 与游戏，由此推导有重复启动及会话资源冲突风险。

正常 UI 点击后会立即离开 ready，能挡普通连续双击；但 AG4 所述临时 IPC 失败也会让学习页失去启动任务 ID 并回到 ready，因此后端仍必须守住唯一会话约束。

建议：复用既有操作状态，在启动前原子占位，失败/取消释放，成功时交接给学习 session；再次验证也使用同一准入。不需要更改 ETW-first 或快照回退策略。

## AG6：复制中断留下整份无引用本体（P2）

位置：`src-tauri/src/services/add_game_service.rs:69`、`:133`；`src-tauri/src/commands/add_game_commands.rs:139`、`:179`；`src-tauri/src/repositories/task_repository.rs:47`；`src-tauri/src/lib.rs` 的启动恢复调用链。

添加阶段先写 `.<uid>.copying`，完成后改名为正式 UID 目录，再登记游戏和持久化。普通返回错误时有清理，但进程中断不会执行这些分支。

两处窗口未覆盖：

1. 复制中中断：留下 `.copying`。下次添加生成新 UID，不会命中原暂存路径。
2. 本体已经改名、记录尚未持久化时中断：正式目录含完整本体，store 没有这条游戏。

任务仓库重启只把 Pending/Running 改为 Interrupted，既不恢复这些目录，也不建立添加清理任务。全项目 `.copying` 引用仅在复制服务与其单测，启动入口未接入对应恢复。

隔离复现创建第一类残留，再用实际复制函数生成尚未登记的第二类目录，调用实际启动更新清理后，两者均保留。没有真的结束应用或制造 GB 级文件；占空间规模来自实际游戏本体大小，而不是本次测得的数据量。

建议：保存足以绑定本次添加的轻量事务信息，启动时依据任务、记录及目录归属恢复待设置记录或安全回收自己的残留。不能直接按“store 没引用就删除 games 下所有目录”，以免删除尚待其他事务恢复的数据。

## AG7：预检扫描不响应取消（P2）

位置：`src-tauri/src/services/add_game_service.rs:78`、`:80`、`:103`、`:111`。

WalkDir 完整收集所有文件和大小之后，才检查 3 GB、磁盘空间并报告“已扫描”。取消回调第一次出现在复制循环中，扫描阶段完全不调用，也不显示已扫描计数。

实际服务复现：181 个小文件，取消回调从开始就固定为 true。函数仍先报告“已扫描 181 个文件”，进入复制循环后才第一次检查并返回“任务已取消”。原有取消测试只验证最终没有目录残留，不能发现扫描期间按钮长时间没有效果。

建议：扫描循环及时检查取消并节流报告计数；已经取消时不继续来源遍历。超过阈值且需要用户确认时及时结束当前预检，避免为弹提醒继续无意义扫描；保留用户明确要求的全量本体内容，不增加默认文件排除。

## AG8：提交时仍接受取消但最后成功（P2）

位置：`src-tauri/src/services/add_game_service.rs:130`、`:133`；`src-tauri/src/commands/add_game_commands.rs:154`、`:179`、`:199`。

复制完成后的最后一次取消检查与目录提交、记录保存之间没有使用已有 `TaskService::begin_commit`。任务一直可取消，提交阶段收到的请求会设置 cancel_requested，但后台仍写入 PendingSetup 并标记 Success。

隔离复现使用原样添加命令与实际 TaskService，在元数据保存入口触发取消。请求返回成功，最终 task.cancel_requested 为 true，任务却为 Success，游戏已入库。

建议：在不能安全中断的提交边界用现有 begin_commit 原子检查取消并禁用后续取消；此前的扫描、复制继续响应取消。不要在目录已经提交后简单看到取消就直接返回，必须保证本体与记录一致。

## AG9：来源重叠检查漏掉 Windows canonical 形式（P2）

位置：`src-tauri/src/commands/add_game_commands.rs:31`、`:35`、`:106`、`:225`。

来源 canonicalize 后通常带 `\\?\`，当前 games_root 通常是普通盘符形式；局部 paths_overlap 只换斜线并折叠大小写，没有去掉 verbatim 前缀，也没有检查真实父目录别名。命令里两次调用都用同一错误判定。

实际 Windows 复现：在隔离库中建立 `games/existing-game/game.exe`，以其 canonical 来源与普通 games_root 比较，结果是不重叠；再调用原样添加命令，任务成功把现有受管目录复制为新的游戏本体。

本次没有复制包含多款游戏的整个真实库。当前服务先收集文件列表再建立暂存目录，因此不应套用其他模块的“必然无限递归复制自身”结论；这里已经证实的缺陷是受管库内部来源被放行，可能造成重复复制或复制整个库。

建议：复用领域层 normalize_path 与既有真实路径归属校验，统一两侧形式，在后台复制前再次确认；不再维护第三份字符串路径比较。

## AG10：确认提交后的读取失败无法正确重试（P2）

位置：`src/components/AddGameWizard.vue:509`、`:514`、`:515`；`src-tauri/src/commands/save_commands.rs:463`。

confirm 先成功保存保护配置并激活游戏，再单独调用 getGame。若后一次 IPC 读取临时失败，整个 try 进入 catch，页面仍是 review，只显示错误，没有完成回调或“已保存、正在重新读取”的状态。

再次点确认会重做已经成功的提交，后端明确返回“该游戏已经完成设置”；当前向导无法到 done，也无法正常按 PendingSetup 放弃。前端隔离测试复现了“已保存但仍 review → 再次确认必然拒绝”的连续两次调用。

建议：区分提交与提交后刷新。成功提交后保留成功事实，读取失败只重试读取/列表刷新，或利用已返回的配置及当前游戏标识完成返回；不要重复执行不可重复的激活操作。

## 已确认有效的部分

- 普通添加夹具能完成复制，保留启动程序相对路径，并在 store 中登记 PendingSetup；原始来源文件不被修改。
- 本地保护确认使用 with_store_mut 进行候选修改和持久化，普通持久化失败不会先提交内存状态；同一次确认的重入有独立 guard。
- 最终“返回游戏库”走 completed 事件，根组件会清搜索、切回全部游戏并强制刷新。不能把此前的新游戏不显示问题一概归因于最后这个正常成功分支。
- 原添加模块的正常复制、取消后清暂存、显式残留清理、3 GB 边界共 4 项原有测试通过；这些测试没有覆盖本报告的新异常边界。
- 本次没有发现需要改回全量 baseline 的理由。ETW-first、快照回退及此前的原生解析优化仍保留；AG5 发生在学习命令准入与 session 交接处，不是 ETW 事件识别准确性结论。
