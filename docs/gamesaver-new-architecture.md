# GameSaver 新框架设计

> 状态：方案记录
>
> 目标：将 GameSaver 演进为本地优先、云端增强的游戏库平台，提供接近 Steam 的添加、管理、启动、恢复和同步体验。

## 1. 产品定位

GameSaver 不再只是存档备份工具，而是统一管理以下内容：

- 游戏本体；
- 游戏存档；
- 本地版本；
- 云端备份；
- 游戏完整性；
- 一键启动流程。

### 1.1 核心管理单位：游戏

新框架的核心管理单位是“游戏”，不是“存档”。一个游戏实体统一拥有自己的游戏本体、启动配置、存档规则、存档版本、本体版本、云端状态和健康状态：

```text
Game
  ├── 游戏本体
  ├── 启动配置
  ├── 存档保护配置
  ├── 存档版本
  ├── 游戏本体版本
  ├── 云端同步状态
  ├── 完整性状态
  └── 任务记录
```

因此用户的主流程始终围绕游戏展开：

```text
添加游戏
  -> 管理游戏本体
  -> 识别并确认存档范围
  -> 启动游戏
  -> 游戏退出后提交存档版本
  -> 按需更新、恢复或同步游戏
```

存档不再作为独立顶层业务存在。存档规则、版本时间线、恢复和云同步都从当前游戏详情页进入。这样可以让用户始终清楚当前操作属于哪一个游戏，也便于将来扩展本体更新、版本回滚和多云存储。

核心原则：

1. GameSaver 游戏库是默认运行入口。
2. 游戏本体和游戏存档分开管理。
3. 本地数据始终优先，云端是远程副本。
4. 所有高风险文件操作都可验证、可回滚、可恢复。
5. 技术细节隐藏在高级设置中，主流程保持简单。
6. 本次大改允许放弃旧规则兼容，直接使用新的 V3 数据模型。

## 2. 系统分层

```text
前端 UI
  -> Tauri Command 层
    -> 应用服务层
      -> 领域模型与仓储层
        -> 本地文件、CAS 版本库、云端 Provider
```

### 2.1 前端层

负责页面、交互、任务展示和用户确认，不直接实现文件复制、压缩、上传或恢复。

### 2.2 Tauri Command 层

只负责：

- 参数校验；
- 权限和状态检查；
- 调用应用服务；
- 返回结果或后台任务 ID；
- 转换面向前端的 DTO。

### 2.3 应用服务层

按稳定职责划分：

| 服务 | 职责 |
| --- | --- |
| `GameLibraryService` | 添加、复制、移动、删除和查询受管游戏 |
| `SaveService` | 学习规则、扫描存档、提交版本、恢复存档 |
| `LaunchService` | 启动前检查、恢复决策、启动和退出监控 |
| `PackageService` | 游戏本体和存档 ZIP 的生成、校验和解压 |
| `CloudService` | 云端版本、上传、下载、冲突和配额 |
| `IntegrityService` | 游戏清单、文件校验和健康状态 |
| `TaskService` | 长耗时任务、进度、取消、重试和恢复 |

### 2.4 仓储层

负责持久化和外部资源访问：


- GameSaver 本地游戏库；
- 存档 CAS 仓库；
- 游戏本体 ZIP 缓存；
- JSON 或 SQLite 元数据；
- 百度网盘等云端 Provider。

## 3. 本地目录布局

```text
GameSaver/
  games/
    {game_uid}/
      game files...
      .gamesaver/
        manifest.json
        file-index.json
        health.json

  saves/
    .gamesaver-repository/
      objects/sha256/
      manifests/
      refs/

  packages/
    local/
      {game_uid}/{version_id}.zip

  cache/
    icons/
    cloud/
    tasks/

  store.json
```

- `games/{game_uid}`：实际运行的游戏本体。
- `saves/.gamesaver-repository`：存档内容寻址版本库。
- `packages/local`：ZIP 临时文件和可复用的本地包缓存。
- `cache`：可删除的缓存，不作为业务数据来源。
- `store.json`：游戏、规则、任务和云端状态等元数据。

原始游戏目录默认保留，但复制完成后不再作为 GameSaver 的运行目录。

## 4. 受管游戏模型

```text
ManagedGame
  ├── gameUid
  ├── displayName
  ├── managedPath
  ├── executableRelativePath
  ├── lifecycleStatus
  ├── launchArguments
  ├── fileManifest
  ├── saveProfileId
  ├── gameBodyVersions
  ├── latestSaveVersion
  ├── cloudStatus
  ├── healthStatus
  └── lastPlayedAt
```

### 4.1 添加游戏流程

```text
选择原始游戏目录
  -> 检查路径、空间、权限和符号链接
  -> 选择或识别主 EXE
  -> 复制到 GameSaver 暂存目录
  -> 生成游戏文件清单
  -> 启动存档学习
  -> 用户编辑并确认规则
  -> 提交存档配置并正式注册游戏
```

复制过程必须支持进度、取消和失败清理。确认前的游戏使用 `pending_setup` 生命周期，不出现在游戏库且不能启动；目标目录已存在时不得静默覆盖。

## 5. V3 存档规则

旧规则不作为新框架的约束。新的规则直接描述存档范围和排除策略：

### 5.1 必须继承的存档管理能力

新版本不兼容旧规则文件格式，但不能丢失上一版已经验证过的行为和工程经验。以下能力属于 V3 的基础要求，而不是后续可选功能：

- 支持 `%GAME_DIR%`，并始终解析为当前游戏的 `managedPath`；
- 支持 AppData、文档、用户目录等系统已知目录；
- 支持用户选择的自定义目录；
- 支持文件夹级管理，同时允许精确到文件和排除项；
- 支持大文件阈值、默认排除项和黑名单；
- 支持 ETW、快照差异、文件对象关联和目录归类等学习证据；
- 支持 Unicode、日文路径和 Windows 设备路径转换；
- 支持本地 CAS 版本、恢复校验、回滚和版本清理；
- 支持游戏退出后提交一个正式存档版本，而不是频繁创建版本。

规则保存的是路径类型和相对信息，不应过度依赖某台电脑上的固定绝对路径：

```text
managed_game -> 当前 ManagedGame.managedPath
app_data     -> 当前用户 AppData
documents    -> 当前用户 Documents
user_profile -> 当前用户 Profile
custom       -> 用户确认的绝对路径
```

### 5.2 路径失效处理

路径失效时必须显式进入“需要修复”状态，不能静默跳过、删除规则或把空目录当成有效存档：

```text
启动前检查
  -> 发现路径不存在或无法访问
  -> 标记存档规则异常
  -> 展示失效路径和影响范围
  -> 提供重新定位、重新学习或暂时停用
```

处理原则：

- `%GAME_DIR%` 随受管游戏目录变化自动重新解析；
- AppData 和文档路径按当前用户重新解析；
- 自定义路径失效时保留原配置，等待用户重新选择；
- 存档规则存在失效路径时，不得把不存在的路径提交为备份版本；
- 只有部分范围失效时，明确显示已保护和未保护的范围；
- 路径权限不足与路径不存在要显示不同原因；
- 用户修复路径后重新执行一次范围预览和可访问性检查。

```text
SaveProfile
  ├── profileId
  ├── gameUid
  ├── scopes[]
  ├── detectionEvidence
  ├── createdAt
  └── updatedAt

SaveScope
  ├── rootType
  ├── rootPath
  ├── includeFiles
  ├── includeDirectories
  ├── excludeFiles
  ├── excludeDirectories
  ├── excludePatterns
  └── maxFileSize
```

`rootType` 可以是：

- `managed_game`：受管游戏目录；
- `app_data`：应用数据目录；
- `documents`：文档目录；
- `user_profile`：用户目录；
- `custom`：用户明确选择的目录。

添加游戏时使用：

```text
ETW 文件访问证据
  + 快照差异
  + 文件对象关联
  + 目录归类
  + 黑名单规则
  -> 生成候选存档范围
  -> 用户编辑
  -> 保存 SaveProfile
```

规则编辑器必须支持：

- 添加和删除文件、目录；
- 添加白名单和黑名单；
- 查看实际展开后的路径；
- 显示预计文件数量和大小；
- 忽略大文件；
- 恢复默认排除项；
- 保存前预览最终范围。

## 6. 游戏生命周期

### 6.1 启动前

```text
健康检查
  -> 存档状态检查
  -> 本地 / 云端版本比较
  -> 必要时恢复存档
  -> 启动受管游戏
```

默认策略：

- 本地和云端一致：直接启动；
- 云端较新：提示下载恢复；
- 本地较新：提示上传；
- 双方都发生变化：保留两份并要求用户选择；
- 不得无提示覆盖本地存档。

### 6.2 游戏运行中

- 监控游戏进程树；
- ETW 作为保存行为识别和调试证据；
- 不因为普通文件访问频繁创建正式版本；
- 允许未来增加“手动立即保存版本”。

### 6.3 游戏退出后

```text
确认进程树结束
  -> 扫描 SaveProfile 范围
  -> 判断是否发生变化
  -> 创建一个 CAS 存档版本
  -> 后台上传云端
  -> 更新最近游玩和同步状态
```

默认是“一次游戏结束提交一个版本”。没有变化时不创建新版本。云端上传失败不影响游戏关闭。

## 7. 游戏本体版本和 ZIP

ZIP 是游戏本体的备份、传输和恢复载体，不是运行态。运行态始终是：

```text
GameSaver/games/{game_uid}/
```

### 7.1 本体备份

```text
本地游戏目录
  -> 生成文件清单
  -> 排除无关内容
  -> 压缩 ZIP
  -> SHA-256 校验
  -> 分片上传
  -> 写入云端版本记录
```

本体包应排除：

- `localization_work`；
- 日志、缓存和临时目录；
- 崩溃转储；
- 编译缓存；
- 用户明确加入黑名单的内容。

### 7.2 本体版本记录

```text
GameBodyVersion
  ├── versionId
  ├── gameUid
  ├── archiveName
  ├── remotePath
  ├── size
  ├── sha256
  ├── fileCount
  ├── excludedItems
  ├── createdAt
  └── uploadStatus
```

### 7.3 本体版本清理

多版本必须提供明确的删除能力，否则游戏本体 ZIP 很容易持续占满磁盘或云端空间。需要区分三类内容：

```text
当前受管游戏目录
  不属于历史版本清理范围

本地 ZIP 缓存
  可以单独清理，清理后仍可从云端下载

云端 ZIP 版本
  可以单独删除，删除后不可从该云端恢复
```

游戏本体版本页提供：

- 删除单个本地版本；
- 删除单个云端版本；
- 同时删除本地和云端版本；
- 保留最近 N 个版本；
- 按占用空间清理最旧版本；
- 清理前预览将释放的本地和云端空间。

清理规则：

- 当前正在运行或正在恢复的版本不能删除；
- 删除前显示版本时间、大小、来源和是否还能回滚；
- 至少保留一个可恢复版本，除非用户明确确认全部删除；
- 删除本体版本不会删除存档规则和存档版本；
- 删除本地 ZIP 不影响当前受管游戏目录；
- 云端删除必须等待相关上传、下载任务结束；
- 清理失败时保留版本记录，并明确标记“删除未完成”；
- 清理完成后重新读取本地和云端列表，不能只依赖前端缓存。

默认保留策略建议独立配置：本地缓存默认保留最近 2 个，云端本体版本默认保留最近 3 个。存档版本使用独立的保留策略，不与游戏本体版本混合计算。

### 7.4 本体恢复

```text
下载 ZIP
  -> 写入临时文件
  -> 校验 SHA-256
  -> 解压到临时目录
  -> 校验文件清单
  -> 保留当前游戏目录
  -> 原子替换受管目录
  -> 恢复存档
```

ZIP 内固定使用一个游戏根目录，禁止路径穿越和不安全的符号链接。

## 8. 存档版本和云同步

游戏本体和游戏存档都可以上云，但频率和用途不同：

| 内容 | 特点 | 默认行为 |
| --- | --- | --- |
| 游戏本体 | 大文件、低频 | 手动或首次添加后上传 |
| 游戏存档 | 小文件、高频 | 游戏退出后自动上传 |

云端存档路径示例：

```text
/apps/GameSaver/saves/{game_uid}/{save_version_id}.zip
```

存档仍以本地 CAS 为主库，百度网盘是远程版本副本。云端上传失败、离线或 token 过期时，游戏仍可正常使用本地存档。

## 9. 云端 Provider

百度网盘客户端不应和游戏库、存档逻辑耦合：

```text
CloudProvider
  ├── authorize()
  ├── status()
  ├── upload()
  ├── download()
  ├── listVersions()
  ├── delete()
  └── quota()
```

第一版实现百度网盘，后续可以加入 WebDAV、OneDrive 或其他服务，而不改变上层模型。

云端凭据要求：

- 前端不接触 secret key；
- 本地只保存必要 token；
- token 失效时明确提示重新授权；
- 上传和下载均使用临时文件与哈希校验；
- 后续增加 ZIP 加密，保护敏感存档。

## 10. 完整性保护

每个受管游戏维护文件清单：

```text
relativePath
size
modifiedTime
sha256
```

检查分为三级：

```text
快速检查：文件存在、大小和修改时间
标准检查：主 EXE 和关键文件 SHA-256
完整检查：全目录 SHA-256
```

默认启动使用快速检查，用户需要时再执行完整检查，避免每次启动扫描大型游戏目录。

## 11. 任务系统

以下操作统一进入后台任务中心：

- 复制游戏；
- 压缩游戏；
- 上传或下载游戏本体；
- 恢复游戏本体；
- 分析存档；
- 上传存档；
- 清理旧版本；
- 完整性检查。

其中游戏本体的上传和下载属于高耗时传输任务，应该拥有独立的“传输中心”页面，而不是只依赖弹窗或 toast。游戏详情页只负责发起任务和显示摘要，用户离开详情页后仍可以查看和管理任务。

任务模型至少包含：

```text
taskId
taskType
status
progress
currentItem
speed
remaining
error
cancelable
retryable
```

传输任务还应记录：

```text
transferredBytes
totalBytes
percentage
currentFile
fileCount
completedAt
remotePath
```

### 11.1 传输中心

传输中心参考 Steam 的下载页面，定位为独立的全局工作区：

```text
传输中心
  ├── 顶部：总网络速度、总磁盘写入速度、活动任务数量
  ├── 进行中：上传中、下载中、校验中、解压中
  ├── 已完成：最近完成的本体和存档任务
  └── 失败：失败原因、重试和重新授权入口
```

每个任务行至少显示：

- 游戏图标和名称；
- 上传或下载方向；
- 当前阶段，例如“压缩中”“上传中”“校验中”“解压中”；
- 百分比和进度条；
- 已完成大小 / 总大小；
- 当前速度；
- 预计剩余时间；
- 暂停、取消、重试或打开详情操作。

百分比应按阶段分别计算，避免压缩阶段显示长时间停在 0%：

```text
准备       0% - 5%
压缩       5% - 25%
网络传输   25% - 90%
校验       90% - 95%
提交完成   95% - 100%
```

下载恢复时对应显示：

```text
准备 -> 下载 -> SHA-256 校验 -> 解压 -> 文件清单校验 -> 替换完成
```

任务状态和页面导航解耦。窗口关闭后任务继续运行，重新打开传输中心时从后台任务状态恢复展示。

任务要求：

- 关闭窗口后可继续执行；
- 失败后可重试；
- 支持取消和清理临时文件；
- 网络任务支持退避重试；
- 进程异常退出后能识别残留任务；
- 完成后通过 toast 给出简洁结果。
- 任务完成后通过 toast 给出简短结果，并保留完整记录到传输中心。

## 12. 前端应用框架

前端从“功能页面集合”改为“游戏库中心 + 游戏详情空间”。存档不是顶层业务入口，而是当前游戏详情中的一个子模块。用户的主要心智模型是：

```text
选择游戏
  -> 查看游戏状态
  -> 启动游戏
  -> 在游戏详情中管理本体、存档和云端版本
```

整体布局参考 Steam 的库界面，但只保留 GameSaver 真正需要的内容：

```text
AppShell
  ├── Sidebar
  │   ├── 游戏库入口
  │   ├── 搜索和筛选
  │   ├── 收藏 / 最近游玩
  │   └── 添加游戏
  ├── TopBar
  │   ├── 当前区域标题
  │   ├── 全局任务状态
  │   └── 设置入口
  ├── GameLibraryView
  │   ├── GameList
  │   └── GameDetailView
  └── TaskCenter
```

顶层区域只保留：

- 游戏库；
- 添加游戏向导；
- 传输中心；
- GameSaver 平台设置。

以下内容属于游戏详情页的子页面或面板，不作为顶层导航：

- 存档版本；
- 存档规则；
- 游戏本体版本；
- 云端同步；
- 完整性检查；
- 高级诊断。

传输中心是全局区域，因为上传和下载可能跨越多个游戏；但存档规则、存档版本和本体版本仍然属于具体游戏的详情空间。

### 12.1 两类设置窗口

GameSaver 必须区分“平台设置”和“游戏设置”。两者不能共用一套无作用域的设置页面，否则用户无法判断某个开关会影响一个游戏还是整个应用。

```text
GameSaver 平台设置
  作用域：整个应用
  入口：顶栏或侧栏的设置按钮

当前游戏设置
  作用域：当前游戏
  入口：游戏详情页的设置按钮或游戏卡片菜单
```

#### 平台设置

平台设置采用独立窗口或独立全屏面板，参考 Steam 设置界面的信息组织方式：左侧为分类导航，右侧只显示当前分类内容。它只放全局配置，不放某个具体游戏的启动参数或存档规则。

```text
GameSaver 设置
  ├── 常规
  ├── 游戏库
  ├── 存档保护
  ├── 云端同步
  ├── 传输
  ├── 外观
  └── 高级与诊断
```

推荐分类：

| 分类 | 内容 |
| --- | --- |
| 常规 | 启动行为、退出后提交版本、后台任务和通知 |
| 游戏库 | 游戏库根目录、默认添加策略、重复游戏处理 |
| 存档保护 | 默认排除项、大文件阈值、版本保留数量、恢复确认 |
| 云端同步 | 百度网盘授权、远程根目录、自动上传、离线策略 |
| 传输 | 并发任务数、限速、失败重试、临时文件目录 |
| 外观 | 主题、列表密度、封面显示方式和语言 |
| 高级与诊断 | 日志目录、ETW 测试、缓存清理和完整性检查 |

#### 当前游戏设置

当前游戏设置使用当前游戏名称作为窗口标题，左侧分类只展示这个游戏适用的选项。它更接近 Steam 的“游戏属性”页面：

```text
{游戏名称} 设置
  ├── 通用
  ├── 存档保护
  ├── 云端同步
  ├── 游戏本体
  ├── 更新与版本
  ├── 启动选项
  └── 高级
```

当前游戏设置负责：

| 分类 | 内容 |
| --- | --- |
| 通用 | 游戏显示名称、封面、收藏状态和受管目录摘要 |
| 存档保护 | 存档规则、退出后提交、版本保留和恢复确认 |
| 云端同步 | 此游戏是否同步、远程目录、上传策略和冲突策略 |
| 游戏本体 | 本体 ZIP 版本、排除项、完整性检查和恢复操作 |
| 更新与版本 | 本地本体版本、云端本体版本和版本切换 |
| 启动选项 | 主 EXE、启动参数、工作目录和启动前行为 |
| 高级 | 规则展开路径、ETW 证据、游戏专属日志和诊断 |

当前游戏设置不显示百度账号、全局游戏库路径、全局并发数或全局主题等平台级内容。平台设置中的默认值可以被当前游戏设置覆盖，但覆盖关系必须在界面中明确显示。

配置优先级统一为：

```text
平台默认值
  -> 游戏专属覆盖值
    -> 当前任务临时值
```

例如：平台默认启用退出后上传，某个游戏可以单独关闭；平台默认保留 10 个版本，某个游戏可以单独设置为 20 个。

右侧设置页遵循以下布局：

```text
页面标题
  -> 简短当前状态
  -> 按主题分组的设置项
  -> 危险操作单独放在页面底部
```

设置项应优先使用开关、下拉框、路径选择器和数字输入框。涉及文件移动、清理、删除或覆盖时，使用明确的确认弹窗，并展示影响范围。

特别规则：

- 百度网盘账号和授权属于平台设置；当前游戏设置只配置该游戏是否使用云端同步；
- 游戏库路径变更必须先检查空间并提供迁移进度；
- 传输限速和并发设置只影响新任务；
- 存档排除规则的全局默认值不覆盖游戏单独配置；
- ETW、哈希和原始日志默认隐藏在“高级与诊断”；
- 设置变更后即时生效的项目明确显示状态，需重启的项目明确提示。

### 12.2 游戏库

游戏库采用“左侧列表 + 右侧详情”的稳定布局：

#### 游戏主状态

内部状态可以保持细粒度，但游戏库主界面只展示少量用户状态：

```text
需要设置
可启动
处理中
需要处理
```

状态含义：

- `需要设置`：游戏本体、主 EXE 或存档规则尚未准备完成；
- `可启动`：当前游戏可以直接启动，存档保护状态正常；
- `处理中`：正在复制、恢复、更新、压缩、上传或下载；
- `需要处理`：存在路径失效、云端冲突、校验失败或其他需要用户决定的问题。

云端更新、本地更新、存档已保护等内容作为辅助标签显示，不再扩展主状态数量。传输中心和高级诊断可以展示更详细的内部阶段，但游戏卡片、游戏详情首屏和启动前检查共享这四个主状态。

```text
游戏库
  ├── 左侧：游戏列表、搜索、筛选、收藏和最近游玩
  └── 右侧：当前选中游戏的封面、启动操作和状态摘要
```

左侧列表项只显示：

- 图标；
- 游戏名称；
- 简短状态标记；
- 最近游玩时间或任务状态。

右侧首屏优先显示：

- 游戏名称和封面；
- 主操作“启动游戏”；
- 游戏本体状态；
- 存档保护状态；
- 云端同步状态；
- 最近一次存档版本；
- 最近游玩时间。

游戏本体缺失、需要学习规则或存在云端更新时，启动按钮附近显示明确的下一步动作，而不是把用户引导到规则管理页寻找原因。

### 12.3 游戏卡片

卡片只显示用户高频关心的信息：

- 游戏名称；
- 最近游玩时间；
- 启动按钮；
- 存档状态；
- 云端状态；
- 健康状态。

推荐状态文案：

- 可启动；
- 需要设置；
- 正在保护；
- 有云端更新；
- 本地存档较新；
- 游戏本体缺失；
- 正在恢复；
- 需要重新学习。

路径、哈希、ETW 事件和原始诊断日志放在高级详情中。

#### 封面处理

游戏封面统一使用固定展示比例，推荐采用 `16:9`，避免游戏列表因为图片尺寸不同而发生跳动。上传截图时不强制拉伸图片，而是提供裁剪和焦点调整：

- 支持拖动图片位置；
- 支持缩放；
- 支持预览裁剪结果；
- 支持在保存前重新调整主体位置；
- 保存原图，并生成用于界面展示的标准封面图。

封面数据建议保存为：

```text
coverOriginalPath
coverDisplayPath
coverCrop
coverPosition
```

推荐展示尺寸为 `1280x720` 或 `960x540`。对于比例差异较大的图片，默认采用填充裁剪；用户也可以切换为完整显示模式，此时允许边缘留空。禁止直接将原图压缩变形为固定比例。

前端容器必须使用稳定的宽高比，桌面端和窄窗口使用同一套封面数据，通过裁剪参数保证主体不会被意外截掉。

### 12.4 游戏详情页

游戏详情页是本体、存档和云端能力的统一容器。推荐使用页内标签或分段导航：

```text
当前游戏
  ├── 概览
  ├── 存档
  ├── 游戏本体
  └── 高级
```

#### 概览

概览页只提供高频操作：

- 启动游戏；
- 打开受管游戏目录；
- 查看游戏本体是否完整；
- 查看本地和云端存档是否同步；
- 查看最近一次备份结果；
- 进入恢复流程。

#### 存档

存档页统一承载原来分散的存档功能：

- 当前存档保护状态；
- 最近版本和版本时间线；
- 恢复某个存档版本；
- 本地与云端差异；
- 上传、下载和重试同步；
- 存档规则编辑入口；
- 预计文件数量和占用空间。

规则编辑器作为存档页中的“编辑保护范围”操作打开。用户不需要离开当前游戏，也不需要理解 ETW 或快照术语。

#### 游戏本体

游戏本体页承载：

- 受管目录位置；
- 本地文件数量和占用空间；
- 健康检查；
- ZIP 本体版本列表；
- 上传、下载、恢复和删除本体版本；
- “移出 GameSaver”和“删除本体”的明确区分。

游戏本体页还必须提供“更新游戏本体”入口。由于当前无法像 Steam 一样获取网络更新，更新来源由用户手动选择新版游戏文件夹：

```text
选择新版游戏文件夹
  -> 检查目录和主 EXE
  -> 读取已有清单并执行轻量预检
  -> 展示来源、目标、预计空间变化和覆盖范围
  -> 保护并提交当前存档
  -> 暂存复制新版游戏
  -> 恢复受保护存档
  -> 校验文件清单
  -> 替换受管游戏目录
  -> 更新本地版本记录
```

更新规则：

- 新版来源目录不能等于当前受管目录；
- 更新前先检查磁盘空间和源目录可读性；
- 复制到临时目录完成后才替换正式目录；
- `.gamesaver` 元数据不能被源目录覆盖；
- 游戏本体更新默认采用整目录替换，不维护 Mod、补丁或用户配置的差异合并；
- 更新前自动创建一次本地存档版本，更新后恢复到暂存目录；
- 更新失败时保留旧游戏目录，不产生半成品；
- 更新完成后重新生成游戏本体清单并执行快速完整性检查；
- 用户可以保留最近一个旧本体版本用于回滚。

更新前必须明确提示：新版文件夹会覆盖当前受管游戏目录中的游戏文件。默认只执行轻量预检，不为了展示详细差异而额外计算全目录哈希。存档属于独立资源，更新前先提交当前存档版本，更新后按 SaveProfile 恢复；游戏本体更新不应改变存档版本历史，也不应默认删除用户存档。

详细的新增、修改和删除文件列表属于高级操作，仅在用户主动请求时执行，并且应复用已有清单或在后台任务中完成，不能阻塞主流程。

#### 高级

高级页才展示：

- 原始目录和受管目录；
- 主 EXE 相对路径；
- 规则展开后的实际路径；
- 文件清单和哈希；
- ETW 事务证据；
- 排除项和诊断日志。

### 12.5 添加游戏向导

```text
1. 选择游戏目录
2. 选择主程序
3. 复制并校验游戏本体
4. 学习存档位置
5. 编辑并确认规则
6. 完成注册
```

向导实时显示文件数量、预计空间、排除项、复制进度、存档候选范围和预计备份大小。

## 13. 健壮性要求

高风险操作统一遵循以下规则：

- 先写临时文件，再原子替换正式文件；
- 恢复前保留当前游戏目录或当前存档；
- 失败时清理临时目录，不删除用户原数据；
- 检查磁盘空间后再复制、解压或恢复；
- 所有 ZIP 解压都进行路径穿越校验；
- 不跟随游戏目录外的符号链接；
- 备份、恢复、清理和迁移共享锁；
- 对象和 ZIP 写入后进行哈希校验；
- 云端版本删除前确认是否仍被其他版本引用；
- 游戏本体和存档版本使用独立的清理策略，并在删除前展示预计释放空间；
- 删除游戏时明确区分“移出 GameSaver”和“删除本体”；
- 操作失败时给出可理解的原因和下一步动作。

## 16. 前端设计规范

本节将 UI/UX skill 的通用要求转化为 GameSaver 的实现约束。它服务于桌面端游戏库，不追求照搬 Steam，而是保持“游戏优先、状态清晰、操作可恢复”的体验。

### 16.1 视觉 tokens

所有页面和组件优先使用语义 tokens，不在组件中散落颜色和尺寸常量：

```text
颜色：--surface-app、--surface-panel、--surface-raised、--text-primary、--text-secondary
      --brand、--success、--warning、--danger、--focus-ring
间距：4 / 8 / 12 / 16 / 24 / 32
圆角：4（控件）、8（卡片）、12（对话框）
阴影：sm（列表）、md（浮层）、lg（对话框）
动效：fast 120ms、normal 180ms、slow 260ms；统一使用 opacity 和 transform
```

深色主题必须单独校验对比度，不能通过简单反转颜色生成。文本、边框和状态不能只依靠颜色表达，还要配合图标或文字。

### 16.2 页面优先级

游戏库首屏只突出四件事：封面、名称、当前状态和启动按钮。存档、本体版本、云端和诊断作为游戏详情中的分区或标签页，不在游戏卡片堆叠技术信息。

```text
游戏库       -> 找到游戏并启动
游戏详情     -> 查看状态、管理存档和本体
传输中心     -> 管理跨游戏的上传、下载和恢复任务
平台设置     -> 管理整个 GameSaver
游戏设置     -> 只管理当前游戏
```

每个页面只设置一个主要动作。危险操作使用独立的确认流程，确认内容必须说明影响范围、预计释放空间和是否可撤销。

### 16.3 必须覆盖的状态

页面和组件设计时必须同时考虑：加载、空数据、成功、失败、处理中、取消和部分完成。长任务使用骨架或阶段进度；按钮在请求期间禁用并提供取消或重试入口。

游戏卡片使用统一的用户语言状态：

```text
需要设置 / 可启动 / 处理中 / 需要处理
```

规则、ETW、hash、绝对路径等内容默认折叠到“高级信息”，避免技术细节干扰主流程。

### 16.4 交互和可访问性

- 所有可点击元素有明显 hover、pressed、focus-visible 和 disabled 状态。
- 图标统一使用 Lucide；独立图标按钮必须有 `aria-label` 和 tooltip。
- 键盘 Tab 顺序与视觉顺序一致，弹窗打开后聚焦标题或首个可操作控件，关闭后恢复原焦点。
- Toast 使用非抢占式提示，错误信息同时提供原因和恢复动作。
- 文本允许自然换行；路径、版本号和哈希使用 `overflow-wrap: anywhere`，不撑破布局。
- 动效遵循 `prefers-reduced-motion`，不使用会阻塞输入的动画。

### 16.5 响应式和验收

桌面端以 1024px 以上的侧栏布局为主，窄窗口收敛为单栏；不能出现横向滚动或内容被固定底栏遮挡。固定格式的封面、进度条、按钮和列表行使用稳定尺寸，避免异步数据造成布局跳动。

每个新增页面至少验收：

1. 首屏是否能在 3 秒内理解当前游戏和主要动作；
2. 加载、空、错误、处理中和完成状态是否可操作；
3. 375px、768px、1024px 和宽桌面窗口是否无溢出；
4. 键盘操作、焦点、深色主题和减少动效设置是否可用；
5. 大列表、封面加载和长任务是否不会阻塞主界面。
