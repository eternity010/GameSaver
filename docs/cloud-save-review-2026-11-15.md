## CS1：读取失败不应降级为“没有云端存档”

位置：`src-tauri/src/services/cloud_save_service.rs:544`、`:549`、`:554`、`:285`、`:342`。

`fetch_manifest` 对目录列表错误使用 `unwrap_or_default()`。清单下载、读取和 JSON 解析失败也不向上传播，而是继续按 ZIP 文件名构造简化清单，或者返回 `None`。

例如旧清单已有多个版本，本次存档包上传成功，随后目录读取因临时网络或授权问题失败；调用方会把 `None` 当作首次同步，构造只包含本次版本的新清单。如果之后的清单上传恢复成功，旧版本索引会被覆盖。旧 ZIP 可能仍在网盘，却不能正常通过历史清单查看和管理。单纯查看时也可能误显示“没有云存档”。

清单下载或解析失败后构造的简化条目还丢失整包 SHA-256、文件数和解压大小，并且直接使用目录列表顺序；后续读取无法区分真正的旧数据与临时读取失败。

建议：明确区分目录确实不存在、清单确实缺失、网络错误、授权失败和清单损坏。正常上传及恢复必须传播读取错误；清单重建应是独立、明确的修复动作，读取包内元数据后再提交，不能作为静默兜底。

## CS2：运行中恢复可以绕过前端限制

位置：`src-tauri/src/commands/cloud_save_commands.rs:203`、`:235`、`:370`；`src-tauri/src/app_state.rs:146`；`src/components/TransferCenter.vue:91`。

详情页在游戏运行时禁用恢复，但后端恢复入口只认领云操作锁，没有检查 `running_games` 或学习会话。`CloudOperationClaim` 仅检查其他操作锁，不检查游戏是否正在运行。

实际可达路径：保留一条失败的云端恢复任务，启动游戏，再到传输中心重试。重试分支直接调用 `startRestoreCloudSaveTask`，不检查运行状态，也没有重新提示当前恢复会覆盖存档。后端随后仍能下载并执行物理恢复。

启动侧虽然会阻止“恢复已经开始后再启动游戏”，但不能阻止相反的顺序。游戏可能继续将内存中的旧状态写回磁盘，导致恢复结果被覆盖，或在恢复期间读到切换中的存档。

建议：对物理恢复增加后端运行/学习状态校验，采用与启动一致的锁顺序，避免检查与启动之间留下竞态；恢复线程在写盘前再次确认。上传已提交的 CAS 版本与物理恢复应分别制定运行状态要求，不必一律禁止运行时上传。

## CS3：清单提交失败前已经删除旧包

位置：`src-tauri/src/services/cloud_save_service.rs:321`、`:325`、`:342`。

上传流程先上传新 ZIP，再读取并更新清单，然后删除超出保留数量的旧 ZIP，最后才保存新清单。

例如保留数量为 1，云端当前只有 A；本次 B 上传完成并删除 A，随后新清单上传失败。远端旧清单仍引用已删除的 A，而 B 已存在但不在清单中。任务虽然显示上传失败，之前可恢复的版本列表也已失效。

建议：先提交包含新版本和待回收旧版本的完整清单，确认新版本可发现，再执行旧包回收并更新清单。删除或最终清单收尾失败时，应保留可重试的清理信息并与远端实际文件核对；不能把新版本能否登记放在删除旧包之后。

## CS4：多个存档范围中的同名文件无法打包

位置：`src-tauri/src/services/cloud_save_service.rs:232`、`:235`、`:786`。

本地 `SaveFileEntry` 以 `root_type + root_path + relative_path` 区分位置，但 ZIP 名称固定为 `data/{relative_path}`，没有携带存档范围或对象身份。

例如游戏目录和 LocalLow 两个范围各有 `slot.dat`，会同时写入 `data/slot.dat`。当前使用的 zip 2.x 写入器直接返回 `Duplicate filename`，因此这种合法的本地版本无法上传。下载校验也只以相对路径作为键，同样会判重复。

此外，`package_save_version` 在创建临时 ZIP 后发生错误，没有临时文件守卫；调用者只有等该函数成功返回后才拿到路径并负责清理，打包失败可能在系统临时目录留下 ZIP。

建议：包内以对象哈希或确定的范围槽位组织数据，由元数据关联回完整条目身份，上传与下载共用同一约定；给打包阶段自身增加失败清理守卫。

## CS5：取消按钮与执行线程没有接通

位置：`src/taskFeed.ts:34`；`src-tauri/src/commands/cloud_save_commands.rs:363`、`:394`；`src-tauri/src/services/cloud_save_service.rs:498`。

传输中心把 `cloud_save_sync` 标为可取消，后端 `cancel_task` 也会设置 `cancel_requested`。但上传和恢复 worker 的进度回调始终返回 `true`，不调用 `TaskService::is_cancelled`。服务在导入结束、保护当前存档、物理恢复和提交前，也没有响应取消的判定。

结果是用户确认取消后，上传仍可完成，恢复仍可覆盖本地存档，最后任务还可能显示成功。将进度回调改为读取取消标记仍不够：服务有多处忽略回调返回值，物理恢复也需要明确不能取消的提交边界。

建议：下载、打包、对象导入阶段接通取消；进入物理恢复前设置明确的取消检查点。物理恢复和最终提交期间禁用取消或延后处理取消请求，终态应区分 `Cancelled` 与普通失败。

## CS6：当前本地存档与最近创建的版本被混为一谈

位置：`src-tauri/src/services/cloud_save_service.rs:690`、`:717`、`:731`、`:743`；`src/components/GameDetailPage.vue:374`。

`get_overview` 将本地历史按创建时间降序排列，状态构造函数选择第一项，没有使用游戏的 `latest_save_version_id`。详情页“同步最新”同样上传 `versions[0]`，没有选择已由后端标明的 `isCurrent` 项。

用户恢复旧版本之后，当前磁盘对应的基线并不是最近创建的版本。云端还原本身还会先创建一份较新的“恢复前保护版本”，随后把当前指针设为选定云端版本。此时状态可能声称“本地有待同步新存档”，用户点同步却上传了恢复前的数据，而不是刚恢复后的当前版本。反过来，本地保留了已上传的新历史但当前使用旧版本时，也可能误报“已同步”。

另一个确定性问题是 `loc.version_id == cld.version_id || loc_time == cld_time`：当前时间戳为秒级，不同版本同秒创建就会被判定为已同步，内容与版本 ID 均没有确认。创建时间不能充当相同版本的证明。

建议：按当前基线判断本地有效状态和默认上传对象；历史数量单独展示。相同版本以版本 ID 或内容身份确认，时间仅用于排序和提示，不能据此跳过同步。

## CS7：纯删除版本上传后无法从云端恢复

位置：`src-tauri/src/repositories/save_repository.rs:127`；`src-tauri/src/services/cloud_save_service.rs:232`、`:307`、`:778`、`:793`。

本地版本库允许只含 `deleted: true` 条目的版本，用于表示用户清空全部受保护存档。恢复规划也能让仅由删除条目引用的现存范围参与清理；现有 `restore_registers_a_root_that_only_tombstones_reference` 测试覆盖了该能力。

上传会生成只含 `meta.json` 的 ZIP，按零个活文件写入云清单并正常完成。但下载校验只构造未删除文件的集合，随后因集合为空直接报“存档版本没有可恢复的文件”。因此同一份合法状态在本地可以表达和恢复，到云端就无法还原。

建议：区分真正无效的空版本与经过验证的纯删除版本，保留删除条目的范围身份，并复用现有受保护范围清理及事务回滚逻辑；无法安全定位的历史路径仍应拒绝清理或保守跳过。

## 已确认有效的保护

- 下载的存档文件会比对对象 SHA-256，写入 CAS 时再次校验对象内容；有有效预期整包哈希时也会对比 ZIP SHA-256。
- ZIP 条目读取有大小上限及声明大小比对；路径穿越、重复数据条目、缺少声明文件会报错。
- 对象导入期间已使用待提交对象保护，避免并发 GC 提前回收。
- 同一游戏的云存档操作已有进程内互斥，普通早退通过认领守卫释放锁。
- 物理恢复使用已有事务及回滚收据，当前存档先受保护，记录持久化失败会尝试回滚。
- 新机器缺少常见标准存档目录时，本地恢复层可创建目录；多作用域路径歧义会拒绝，而非随意选一个写入。

这些保护应保留，不需要为修复本轮问题重写整个存档仓库。
